OmniRoute routes a request. KeepRoute owns the mission. When Claude hits a limit, OmniRoute can switch models, KeepRoute can keep the same job alive with checkpoints, remaining work, and a handoff to another agent so you are not copy-pasting progress by hand.

Why KeepRoute was made

OmniRoute solves traffic. KeepRoute solves unfinished work.

People already had a great way to send chat to many AIs. What kept breaking real Keep workflows was not “pick a model”, it was losing the job when that model hit a wall.

OmniRoute

Chooses where this request goes among providers and models.

KeepRoute

Owns the whole job, watches it, checkpoints it, and continues it if the AI has to change.

OmniRoute moves packets of AI work. KeepRoute moves missions. Same underlying gateway. Different job: continuity under failure.

The problem we kept hitting

A coding session would be halfway done. Claude hit quota. Or Cursor stalled. Or the host rebooted. Stock routing can send the next prompt somewhere else, but the human still had to rebuild context: what finished, what failed, what files mattered, what not to do twice.

Why not “just use OmniRoute”?

You should, KeepRoute does. OmniRoute is the traffic director. KeepRoute is mission control. Without KeepRoute you still have excellent fallback between models. With KeepRoute the job itself has an ID, memory, and a recovery path.

What we refused to accept

Trivial “hi” burning paid tokens. Clients each inventing their own routing rules. Starting over after a recoverable failure. Replaying a destructive step because the new agent did not know it already ran.

The design bet

The mission is the product. The model is replaceable. KeepRoute exists so OtaconsKeep can treat Claude, Codex, Cursor, Grok, and Local as executors, not as the owner of your work.

What does it actually do?

You describe the job. KeepRoute keeps the mission alive.

You tell the system what you want done. It chooses an appropriate AI or local model. If that provider hits a limit, crashes, or becomes unavailable, the job can continue through another compatible agent, without making you start over.

This does not mean every provider or every task is guaranteed to hand off perfectly. Handoff quality still depends on tool compatibility and what the mission has saved.

If needed again: Codex → failure → Cursor → same mission continues. Completed work, remaining tasks, errors, and files travel with the mission, not private “hidden reasoning” from the previous model.

Why this design exists

Providers are powerful. Each one still has limits.

Quotas, rate limits, outages, context limits, different strengths, different tools. KeepRoute separates the mission from the provider. The job belongs to the orchestration layer, not to Claude, Codex, Cursor, Grok, or any single model.

That means the system can choose the right executor, preserve progress, and move the mission when conditions change.

What did KeepRoute improve?

From disposable requests to durable missions

Requests became Missions

Long-running work gets a persistent Mission ID and state instead of living only inside one model call.

Routing became policy-controlled

Clients no longer secretly choose providers. One orchestration layer owns routing policy.

Failures became recoverable

Rate limits, quota issues, timeouts, and supported runtime failures can trigger controlled recovery instead of forcing a restart.

Provider fallback became continuation

Not merely retrying a prompt elsewhere, completed work, errors, checkpoints, files, and remaining tasks can be preserved.

Models became interchangeable executors

A mission can outlive the individual AI currently performing it.

Local AI became the default for cheap work

Simple requests can stay local instead of unnecessarily consuming paid-provider usage.

Restarts stopped killing the mission

Persistent state allows supported missions to survive service restart and validated host reboot recovery.

Project REX · latest advancement

KeepRoute / OmniRoute can feed REX research — on the full Keep

Traced end-to-end on the operator Keep (not marketing theory): every KeepRoute / OmniRoute exchange can record into a shared learning pool. A world-model rebuild turns those records into risks, domain insights, and proposal sources. Project REX’s governance loop treats world_model:* as a first-class proposal source — same board pipeline as other REX work. That is aiding and driving R&D: routing outcomes become durable signal, not a disposable log line.

Driving + aiding

OmniRoute moves the request. KeepRoute owns the mission. Learning records the outcome. The world model summarizes it. REX can spawn or rank work from that summary — including KeepRoute-domain risks and low-confidence route patterns.

Global pool, not a local silo

The learning store and world model are one shared pool per Keep install, tagged by domain (for example keeproute). Tags filter; they do not wall off memory. Agents and REX draw from the same pool whether the exchange came from Claude, Codex, Cursor, Grok, or local Ollama through KeepRoute.

Gets smarter with traffic

Failed pre-flight / route attempts become risk signal. Successful exchanges after a fix dilute stale failure weight as fresher records accumulate. That is the practical “smarter over time” loop — success and failure both teach the board.

Why OmniRoute · why not Jev

We need a local gateway, not a cloud judgment model

OmniRoute and Jev both get mentioned in “AI routing” conversations, but they solve different problems. KeepRoute needs a local multi-provider data plane that Claude, Codex, Cursor, Grok, and Ollama can actually talk to. Jev is a typed decision / judgment layer (TypeSafe AI) that scores complexity, gates tool calls, and advises which model tier to use, usually via cloud gateway or MCP. Useful elsewhere. Wrong job for KeepRoute’s foundation.

Jev (TypeSafe AI)

A decision model: classify the turn, pick fast / balanced / deep, gate risky tools, review patches. Host agent still owns files and commands.

Cloud / MCP · judgments · waitlist / gateway keys

VS

OmniRoute (upstream)

A local OpenAI-compatible gateway: one endpoint, many providers, combos, fallback, health, and circuit handling on hardware you control.

Self-hosted · provider traffic · keys stay local

What OmniRoute gives KeepRoute

A real data plane on 127.0.0.1: providers connected once, Auto routing, fallbacks when Claude hits quota, local models for cheap work. KeepRoute’s Mission Controller sits on top of that plane. Without a gateway like OmniRoute, there is nothing durable to hand a mission to when the executor changes.

What Jev actually is

Jev answers typed questions: next step, risk, model tier, tool allow/block. It does not run your Claude/Codex/Cursor sessions, hold provider API keys on your LAN, or expose an OpenAI-compatible proxy your Keep UI can stream through. It is middleware advice, not the traffic pipe KeepRoute wraps.

Why OmniRoute wins for this stack

Local-first and offline-capable. Provider keys and routing stay on your machine. No waitlist for the core path. Works with the same agent CLIs OtaconsKeep already uses. Open source, Docker-friendly, and already proven under KeepRoute’s soak tests. Jev still needs a host model and usually a cloud gateway bill for the judgments themselves.

Can they coexist?

Yes, in theory. You could ask Jev “is this turn deep enough for Opus?” while OmniRoute still carries the request. That does not replace OmniRoute. KeepRoute’s bet is mission continuity on a self-hosted gateway, not outsourcing every routing judgment to a third-party decision model.

Security / privacy

What we claim, and what we do not

We do not claim “everything is encrypted.” Public static website assets are not part of an encryption-at-rest story. Below is an honest control map for KeepRoute deployments.

Design intent

Provider credentials stay server-side

API keys and provider secrets must not be shipped to the browser or embedded in public pages.

Design intent

Public client vs private data plane

Internal routing data-plane services are intended for private/local binding, not for casual public exposure.

This page

Sanitized public diagnostics

This site publishes aggregate release results only. No raw mission payloads, logs, or credentials.

This page

No secrets in frontend bundles

Static HTML/CSS/JS for this page contain no API keys, tokens, or private remotes.

Not verified (do not claim)

Encryption of all mission state at rest

Full-disk / field-level encryption of every mission record is not claimed as a verified KeepRoute 1.0 guarantee.

Not verified (do not claim)

Encrypted backups of all sensitive state

Operators should apply their own backup encryption. KeepRoute 1.0 does not advertise a verified universal backup-crypto product feature.

Deployment-dependent

TLS across every trust boundary

Use TLS wherever traffic crosses an exposed network. Local-only installs may use loopback without public TLS, that is a deployment choice, not a magic shield.

Operator practice

Least privilege & auth for admin surfaces

Administrative APIs and dashboards should be authenticated and not published as open internet endpoints.

If a control is marked Not verified, we will not market it as finished. Prefer honest gaps over false confidence.

Pros & cons

Straightforward tradeoffs

Pros

  • Automatic routing with policy
  • Local-first inexpensive tasks
  • Stateful missions
  • Provider failover with continuation
  • Agent-runtime handoff (supported paths)
  • Restart / reboot recovery (tested)
  • Checkpointing
  • Less manual copying between agents
  • Route history and visibility
  • Avoids repeating completed destructive operations
  • Provider independence at the mission layer

Cons

  • More components than stock OmniRoute alone
  • Requires the Mission Controller layer
  • More storage/state to manage
  • Handoff quality depends on provider/tool compatibility
  • More setup than a single-provider workflow
  • Local inference needs adequate hardware
  • Cloud providers still have their own limits and costs
  • Recovery adds some latency
  • Not every external agent exposes identical capabilities

Limitations

Read this before you install

  • No AI system is guaranteed to finish every task.
  • A replacement agent cannot inherit another provider’s private hidden reasoning.
  • Handoff uses provider-independent mission state: files, decisions, errors, TODOs, tool results, and checkpoints.
  • Provider APIs and services may change without notice.
  • Some tasks require provider-specific tools and may not be transferable.
  • Local model quality depends on hardware and model choice.
  • Cloud usage can cost money.
  • Internet/provider outages can exhaust all available routes; the mission should stop cleanly rather than pretend success.
  • Checkpoints reduce risk but are not a substitute for backups.
  • Arbitrary destructive commands still require appropriate safety policy.
  • Benchmarks are release-test results, not universal performance guarantees.
  • Accepted residual operational notes (public-safe): occasional warm-up delay after a machine boots; cosmetic health-check noise on the upstream gateway container; intentional private binding of the internal data plane. These are monitored, low-severity, and not claimed as Sev-1 product failures.

Start OmniRoute (the routing engine)

  1. Still inside the KeepRoute-UI folder, pick a strong first-login password (yours alone, not an example from the internet): 
    export OMNIROUTE_INITIAL_PASSWORD='pick-a-strong-password'
  2. Start OmniRoute with Docker Compose: 
    docker compose -f docker-compose.omniroute.yml up -d
  3. Confirm the container is up: 
    docker ps | grep -i omni
    You should see a running container line. If not, scroll to If something fails.
  4. OmniRoute listens on your machine at http://127.0.0.1:20127 (loopback only). Open that URL in a browser if a dashboard appears, sign in with the password you set, and connect providers there (Claude / OpenAI / Cursor / xAI / Ollama, etc.).
  5. Product write-up: KeepRoute on GitHub. Upstream gateway: OmniRoute on GitHub.

Install Python deps and start the KeepRoute UI

  1. Still in the KeepRoute-UI folder, install Flask for your user: 
    python3 -m pip install --user flask

    mkdir -p desk/state
echo '{}' > desk/state/credentials.json
chmod 600 desk/state/credentials.json
  3. Point KeepRoute at OmniRoute and start the UI (leave this terminal open):

FAQ

Practical questions

Why does KeepRoute exist if OmniRoute already routes?

OmniRoute routes a request. KeepRoute owns the mission. We built KeepRoute because long agent jobs kept dying when Claude hit a limit, a provider failed, or the host restarted. Stock routing can send the next prompt elsewhere, KeepRoute checkpoints the job and continues it so you are not rebuilding progress by hand.

Is there a GitHub write-up?

Yes, github.com/Otaconskeep/KeepRoute has the full product write-up, INSTALL.md how-to, WHY doc, and the KeepRoute-UI package you can clone. This page mirrors the install path with screenshots.

Is this stock OmniRoute?

No. It uses stock OmniRoute as its underlying provider/model routing data plane and adds a stateful Mission Controller and orchestration layer (KeepRoute). Same family of gateway; different product job.

Did you fork OmniRoute?

KeepRoute extends OmniRoute with an independent stateful orchestration/control layer. We do not present KeepRoute as “our OmniRoute fork.” Upstream OmniRoute remains its own project, KeepRoute is OtaconsKeep’s mission layer on top.

Why OmniRoute instead of Jev?

Different layers. Jev (TypeSafe AI) is a cloud/MCP decision model that judges complexity and tool risk. OmniRoute is a local multi-provider gateway that actually carries Claude / Codex / Cursor / Grok / Ollama traffic. KeepRoute needs that local pipe for missions and keys. Jev can advise a host agent; it cannot replace OmniRoute as the KeepRoute data plane. Full comparison: Why OmniRoute · why not Jev.

What happens when Claude reaches its limit?

KeepRoute can checkpoint the mission and continue on another eligible provider/agent when the path is supported. That is different from simply retrying the same prompt blindly.

Can it use Cursor?

Yes, as a supported agent adapter path when configured. Not every Cursor capability is identical to every other agent.

What if everything is offline?

The mission should stop cleanly rather than pretending it succeeded.

Can I run everything locally?

Simple work can stay local. Heavy coding/agent work may still need cloud providers depending on your hardware and models.

Does it guarantee my code won’t break?

No.

Does it guarantee every mission completes?

No. Release tests showed strong results in the measured samples; they are not a universal guarantee.

Are my API keys public?

No. Keys must stay server-side and protected. Never paste them into a public webpage or chat.
